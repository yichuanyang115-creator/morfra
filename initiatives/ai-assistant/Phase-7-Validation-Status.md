## 1. 这份记录的作用

这不是新需求、缺陷清单或主产品接入批准。它只保留 Phase 7 的实际验证结论，避免以后把“尚未具备验证条件”误说成“已经通过”或“功能有问题”。

根 `Product-Spec.md`、根 `DEV-PLAN.md`、主产品数据模型和路由均未因此修改。主产品接入仍受 `INTEGRATION-CONTRACT.md` 的准入条件约束。

## 2. 已通过的独立验收

| 用户可感知的结果 | 实际证据 |
| --- | --- |
| AI 只读取当前表的字段与记录，不读取详情正文、Tab 或附件内容 | 当前宿主适配器、运行时契约检查与跨表隔离测试通过 |
| AI 可打开记录详情，不直接控制详情页面 | 宿主动作与引用跳转测试通过 |
| 旧对话文件只继承 AI 面板的打开状态和宽度 | 旧假消息不迁入，新偏好写入独立位置，旧文件保持不变的测试通过 |
| 删除表时不会留下找不到所属表的 AI 历史 | 顺序为“先清理 AI 历史，再删除表，最后刷新页面”；失败会阻止删表的测试通过 |
| 精确计算、引用、错误处理、选择范围和跨表隔离可被本地验证 | 固定 20 项评估集实际执行并通过 |
| 密钥不会写入普通文件、会话或前端状态 | 静态扫描、持久化测试和 Rust 命令边界测试通过；Key 仅设计为进入系统钥匙串 |
| 打包后的应用能正常显示 AI | Tauri macOS `.app` 构建成功；生产应用中已验证当前表、详情与 AI 切换、设置入口、主题切换、面板关闭/重开和重启恢复 |

## 3. 条件性验收门槛

以下项目不是已知缺陷。它们必须在对应前提具备后恢复验证；在完成前不得把 AI 标为“已完成主产品接入”。

| 等待条件 | 之后要确认的用户体验 | 合格证据 |
| --- | --- | --- |
| 主产品能安全提供至少两张表和一张可删除的测试表 | 切到另一张表后，AI 只显示新表的内容和历史；删除测试表后，AI 历史一起消失，其他表历史仍在 | 打包应用中的切表、删除前后记录和自动化删除级联测试 |
| 可把打包应用调整到窄窗口 | AI 以可关闭的覆盖面板出现，不挤压表格和详情到无法操作 | 窄窗口截图/录屏与“打开、关闭、详情切换”的实际操作结果 |
| 用户准备好专用测试服务与测试 Key | 用户配置服务后，Key 只显示“已配置”；关闭重开后仍可用，但页面、文件和日志中没有 Key 明文 | 用户手动输入 Key 后的 Keychain 状态、文件扫描和重启结果 |
| 用户明确执行一次测试提问 | 只有提问或测试连接时才联网；流式回答可停止；记录引用能跳回正确详情 | 真实服务上的一次正常回答、一次停止、一次引用跳转和网络触发时机记录 |

## 4. 恢复验收规则

1. 不用假表、假消息、测试 Key 或“应该可以”替代上表的真实结果。
2. 删除验证只能针对用户明确指定的测试表；不得删除用户已有数据。
3. 录入 Key 必须由用户本人完成；验收人员只检查状态和行为，不读取 Key 明文。
4. 任一项失败时记录实际现象、表 ID 和复现步骤，并从对应修复后的 Stage 1 重新审查。
5. 四项都完成后，仍需主流程单独批准根需求、根计划和接入阶段，才可把 AI 合入主产品。

AI 独立工作流的实现、质量评估和可安全验证的生产体验已经收口。其余项目保留为主产品能力与真实服务准备好之后的接入验收门槛，不应被当成 Phase 8、普通产品待办或现有功能故障。
